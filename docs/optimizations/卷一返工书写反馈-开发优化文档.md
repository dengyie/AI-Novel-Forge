## 0. 为什么是「书写反馈」驱动，而不是凭代码扫描

这一轮的价值在于：**很多缺陷只有真的去写一章才暴露**。最典型的是 writer 超时——短续写 probe 全过，整章 draft 直接撞墙。这说明：

- 代码扫描能发现结构问题，发现不了**吞吐量假设与现实不匹配**。
- probe（短样本）会系统性掩盖**只有长样本才触发**的欠配。
- 因此本文档的每一条开放缺陷，都要求附「在什么书写场景下暴露」「为什么 probe 漏掉」，避免后续又被短样本误导。

## 1. 本轮书写经验复盘：writer 超时「假挂死」

### 1.1 症状链（生产实录）

ch3 返工首次用 `gemini-3.7-flash-high` 跑 ~8000 字章节，writer 在 `[novel.chapter.writer@v5] Request timed out after 480000ms` 处被墙钟掐断，流到 6493/8000 字（81%）、草稿未落库、整章返工卡住。

### 1.2 三层同步验证（pxed 生产栈 + cpa + gemini-3.7-flash-high）

| 层 | 方法 | 结果 |
|---|---|---|
| L1 线缆 | `curl` 直连 cpa（continue，max_tokens=16384，include_usage） | 13–23s 200 OK |
| L2 裸调用 | `llm.stream` 重放（不经装饰栈） | establish +9.1s，DONE +21.8s，72 chunk |
| L3 装饰栈 | `attachLLMUsageTracking` 包装 + `runWithEnforcedTimeout` 的 `controller.signal` 内层重放 | establish +11.4s，DONE +19.6s，63 chunk，**零挂死** |

**结论**：线缆、LangChain 核心、装饰栈、AbortSignal 全部健康。所谓「挂死」不存在。

### 1.3 根因：超时预算公式对 gemini 过度乐观

实证位置 `server/src/services/novel/chapterWritingGraph.ts:50-63`：

```
WRITER_TIMEOUT_MIN_MS      = 480_000
WRITER_TIMEOUT_MAX_MS      = 1_500_000
WRITER_CHARS_PER_SECOND    = 25            // ← 单一硬编码常量
WRITER_TIMEOUT_HEADROOM    = 1.6
resolveWriterTimeoutMs(t) = min(MAX, max(MIN, ceil(t/25 * 1000 * 1.6)))
```

- gemini-3.7-flash-high 经 cpa 实测 **~13.5 字/秒**；公式假设 25 字/秒 → **乐观 ~1.85×**。
- 8000 字整章实际需 `8000/13.5 ≈ 593s`；draft 预算 `8000/25*1.6 = 512s` → **撞墙**。
- 生产流到 81% 被掐断，与 13.5 字/秒精确吻合（512s × 13.5 ≈ 6912 字，扣建立/收束开销落在 6500 量级）。

### 1.4 为什么 probe 全过但生产挂

probe 测的都是**短续写**（~1500 字，~20s 完成），公式给的 floor 480s 绰绰有余。只有**整章 draft 或长缺口 extend** 才把公式逼到真实吞吐线上。这是本轮最可复用的方法论结论：**任何与吞吐/预算相关的验证，必须用生产量级样本，不能用短样本当绿灯。**

### 1.5 生产处置（已授权）

经用户授权（2026-08-16），pxed `.env` 第 105 行 `LLM_REQUEST_TIMEOUT_MS` 由 `480000` 提到 `1200000`（20 分钟，上限 3600000），备份 `/tmp/server.env.bak-LLMTO-20260816T085634Z`，重启 `novel-server` 生效，`/proc/<pid>/environ` 复核。**注意：这是缓解，不是根治**——环境变量抬高了 floor，但公式本身的乐观假设未动；换更慢的模型或更长章节仍会复发。

## 3. 真实开放缺陷（按证据强度排序）

### D1（最高）writer 超时预算公式：单一乐观常量 — **已闭环**

> 实现见 §2「已闭环」表。新增 `server/src/services/novel/writerTimeoutBudget.ts`：`resolveWriterTimeoutMs({ targetWordCount, provider, model })`，吞吐按 **model 维度**登记实测值（gemini-3.7-flash-high=13.5、deepseek-v4-pro=15 字/秒），未知 model 回落保守默认 13.5（不乐观于已知最慢），floor 480s / ceiling 1500s / headroom 1.6 语义不变。`chapterWritingGraph.ts` 旧常量与旧 `resolveWriterTimeoutMs` 已删，draft（:709）与 extend（:457）统一走新 factory 并传 model。测试 `server/tests/writerTimeoutBudget.test.js` 8 断言（floor / probe 不退化 / gemini 预算超旧 512s 撞墙预算 / 实测吞吐精确匹配 / 未知 model 保守 / ceiling 钳制 / 单调 / deepseek 独立吞吐）+ `writerExtendStreaming.test.js` 既有 `>=480_000` floor 断言仍绿。**未碰字数下限/节奏**（产品铁律）。

- **实证**：`chapterWritingGraph.ts:52` `WRITER_CHARS_PER_SECOND = 25`，被 `resolveWriterTimeoutMs`（:55-63）用于 draft（:709）与 extend（:457）两个调用点。gemini 经 cpa 实测 13.5 字/秒，乐观 1.85×。
- **触发场景**：整章 draft（8000 字级）或长缺口 extend。短样本不触发。
- **修复方向（纯预算工程，不碰内容、不碰字数下限）**：
  1. 把单一常量改为 **`(provider, model)` 维度的实测吞吐参数**。gemini≈13.5 先登记为基准；其它模型按实测补。模型变快预算自动放宽，不增加墙钟负担。
  2. extend 的 `target` 当前是 `Math.max(missingWordGap, minWordCount)`（:457）。代码注释（:492）明确这是**有意的保守下界**，目的是防短 gap 撞 480s 墙——**保留这个保守语义**，但下界本身要由「实测吞吐」驱动，而不是乐观常量驱动。
  3. 把 draft 与 extend 的预算来源统一到同一个 budget factory，避免两处各写各的漂移。
- **测试缺口**：`resolveWriterTimeoutMs` / `WRITER_CHARS_PER_SECOND` 当前**零覆盖**（`server/tests` 下无任何引用）。`writerExtendStreaming.test.js` 只断言 `timeoutMs >= 480_000` 的 floor，不覆盖公式曲线。**修复必须同时补 `node:test` 用例**（禁 pytest）：覆盖 floor / ceiling / 曲线 / 不同 model 吞吐。

### D2（中）超时未在质量失败分类中被单独识别 — **已闭环**

> 实现见 §2「已闭环」表。`classifyPromptQualityFailure` 已增加 `timeout` 分支，复用 `transportRetry.isTimeoutLikeTransportError`（识别 `TimeoutError` name + "timed out"/"timeout" 文案 + 泛化 AbortError，并排除显式取消），顺序在 schema 关键词兜底之前，避免含 schema 关键词的超时被抢走。D1 吞吐漂移告警的观测前提已就位。原文（保留作历史）：

- **实证**：`server/src/prompting/observability/PromptExecutionRecorder.ts:25-48` `classifyPromptQualityFailure` 的分支集合为 `{ llm_error, schema_repair_failed, post_validate_failed, empty_output, unknown }`，**无 `timeout` 分支**。超时会被归进 `llm_error`。
- **如实窄化**（不要夸大）：函数**并非完全裸奔**——它在显式标记之外还有 message 字符串兜底（含 `"schema"/"json"/"zod"/"postvalidate"/"semantic"` 等关键词命中）。真实缺陷是：**超时无法从 `llm_error` 里被单独识别**，导致超时专项监控、超时专项重试策略、D1 的吞吐漂移告警都无法挂载到这一个类别上。
- **意图与实现脱节的强证据**：`chapterWritingGraph.ts:459-460` 的注释自述「超时单独归类，让慢与挂在日志里一眼可分」——也就是说**作者原本就打算让超时可分类**，但下游 `classifyPromptQualityFailure` 并没有对应的 timeout 分支落地。这是「有设计意图、无实现兜底」的典型缺口，不是没人想过。
- **修复方向**：增加 `timeout` 分类分支（识别超时错误特征，例如墙钟 abort 的 error 标记或 `timed out` 关键词），让超时与一般 llm_error 在指标/日志里可分。**这是 D1 的观测前提**——先能识别超时，才能量化吞吐漂移。
- **测试缺口**：分类函数零覆盖。

### D3（低-中）质量环持久化 fail-open 的跨进程边缘 — **已闭环**

> 实现见 §2「已闭环」表。catch 块非 setting-debt 分支补对称 stub 落库（`buildNonSettingDebtStubUpdate` 纯函数 + contentRevision CAS 防并发覆盖 + 不动 chapterStatus）。修复时纠正一个关键认知：`recordAssessment` 落库失败的常见触发是 contentRevision 并发冲突（章节已被别路改写），此时「强行补写内存 riskFlags」可能覆盖更新内容对应的新评估——故用 CAS，冲突时安全跳过覆盖。同进程决策不变，只消除「重启后 director 读旧 riskFlags」窗口。原文（保留作历史）：

- **实证**：`server/src/services/novel/pipeline/quality/PipelineChapterQualityPolicy.ts:217-286` 的 catch 块。
- **如实窄化**（已纠正我此前的夸大）：这段**不是「静默吞、纯内存」**。它做了三件可见的事：(1) `logPipelineError("记录章节质量闭环状态失败", …)` 完整结构化告警，含 `failOpenScope: "process_local"`、`projectedGate` 投影、`failOpenMetrics`；(2) 对 **setting-debt 路径** 会二次落库 stub `riskFlags` 并置 `chapterStatus: needs_repair`（:265-280）；(3) 把内存快照写进 `rangeDebtByChapterId` 供同卷后续决策用。
- **真实残留缺陷（窄）**：**非 setting-debt** 的持久化失败路径下，DB 的 `riskFlags` 确实不落库（仅 process_local 内存）。进程重启后，director 自动续写读到的 DB `riskFlags` 是**上一次成功落库的旧值**，可能与内存里的最新评估不一致。影响面：跨重启的质量闭环连续性，不是同进程内的正确性。
- **修复方向**：对非 setting-debt 的持久化失败也补一条「persist-pending + 后台重试」或显式标记 `chapterStatus` 为需要重评估，让重启后能识别「这条 riskFlags 可能过期」。**优先级低于 D1/D2**，因为同进程内决策是对的，只影响重启窗口。

## 5. 产品铁律约束（任何修复方案都不得触碰）

- **不得机械控字数 / 节奏**：D1 的 budget 公式只调「超时预算」，不调「字数下限 / 节奏松紧」。`minWordCount` 是内容契约，不是工程参数，禁止为「防超时」去压字数。
- **不得堆 mode / 灰度**：修复一律走单一清晰路径，不接受「新增一个 conservative mode 先灰度」式的复杂度堆砌。
- **监管只监控不代写**：D2 的超时分类只用于监控/告警/重试策略，不得据此让系统自动改写作者意图。
- **禁「称重」**：本文档及后续 PR 描述一律用「可用性评估 / 吞吐评估」口径。

## 0. 触发方式与端点

卷一返工重写（单章逐章）走 `POST /api/novels/:novelId/chapters/:chapterId/generate`，请求体 `chapterRuntimeRequestSchema`（`server/src/services/novel/runtime/chapterRuntimeSchema.ts:16`）：

```json
{ "provider": "openai", "model": "gemini-3.7-flash-high", "artifactSyncMode": "adaptive" }
```

- gemini-3.7-flash-high 经 CPA 统一出口，provider="openai"（与 D1 实测口径一致，详见 [[writer-timeout-budget-model-throughput]]）。
- 端点 SSE 流式：`data: {"type":"chunk","content":"..."}` 流正文 → `run_status`(finalizing) → `runtime_package` → `done`/`failed`。
- **monitor 监听终态注意**：SSE 会发 `ping` keepalive，**不是终态**；只有 `done`/`failed`/`error`/`complete` 才算终态。第一版 monitor 把 `ping` 误判为终态提前退出（已修正）。

## 1. ch6《真同意》重写经验（2026-08-17）

### 1.3 D3 验证：未触发（无 stub 落库路径）

本次重写后 qualityLoop 正常落库（`source: "repair_recheck"`，`evaluatedAt` 有值），未走 catch 块 stub 落库路径。D3 的 `buildNonSettingDebtStubUpdate` 未触发。需等 recordAssessment 落库失败的场景才能验证 stub 落库日志 `stubRiskFlagsPersisted:true`。

> D2/D3 都是「失败路径」的护栏，正常路径不触发属预期。本次只验证了 D1（正常路径吞吐）。D2/D3 的生产验证需等对应的失败场景出现。

### 1.4 真实发现：重写后 run 终态=failed，质量环判真债（非 D1 超时）

**这是本轮最有价值的经验，必须如实记录。**

ch6 重写 SSE 终态序列：
1. 331 chunk 流式生文 → 13045 字 ✓
2. `run_status` phase=finalizing「正文已生成，正在整理章节文本并保存草稿」
3. `run_status` phase=finalizing「正在完成正文接收检查并同步章节状态」
4. `run_status` **status=failed**, message=**「章节已保存，但检测到待修复问题」**
5. `runtime_package` + `done`（正文已落库 drafted）

**关键认知**：`generate` 端点的 run 终态 `failed` ≠ 生文失败。正文已成功落库（drafted, 13045 字），failed 是**质量检查环节判定有待修复问题**。运维判断时不能只看 run.status=failed 就当生文挂了——要区分「生文失败」与「生文成功但质量环判债」。

### 1.5 质量环判的债是真债，不是误判

ch6 重写后 qualityLoop（`source: "repair_recheck"`）：
- `chapter_retention_contract: risk`（留存信号不足）
- `literary_score: risk`（文学可读门接近但未达 isPass）
- 具体 issueCodes：
  - `coherence:medium:林致远突然出现并手持包子箱、苹果，在追兵逼近的危险现场缺乏合理动机`
  - `pacing:medium:中段林致远对话与食物描写占用较多篇幅，导致追兵逼近的紧张感被稀释`
  - `logic:medium:林致远在危险现场手持食物出现缺乏合理动机`
- 历史 feedback（version 1, blocking, `failedPatchCount: 1, avoidRetry: true`）：
  - `coherence:critical` 中段重复（半开铁门/红光/破木门/水晶球房间复读）
  - `logic:critical`「真同意」触发代价未兑现
  - `logic:high` 结束态要求能力不可控且何屿尚未敢主动使用，正文却…
  - `planHints: 勿无根因连打同路径 patch`

这些是**内容契约/连贯性层面的真债**：林致远出场动机、真同意代价兑现、结束态能力可控性——都是 taskSheet 契约要求与正文落地之间的差距。

### 1.6 经验提炼：avoidRetry=true 时不应连打同路径重写

系统自己在 feedback 里标注 `avoidRetry: true` + `planHints: "勿无根因连打同路径 patch"`。这与监管铁律「卡住先查根因，不无脑重试」完全一致。

**决策**：ch6 不再连打第二次 generate。因为：
1. issueCodes 指向内容契约层面（林致远动机/真同意代价/结束态能力），不是工程超时。
2. `failedPatchCount: 1` + `avoidRetry: true` 表明同路径 patch 已失败过一次，系统已警告勿重打。
3. 监管铁律「监管只监控不代写」——内容契约调整属于质量/重生决策，需用户下令，不是监管层连打 generate 能解的。

**这是「监管只监控不代写」的典型场景**：重写触发了，生文成功了，但质量环判真债，且债的根因在内容契约而非工程层——此时监管应停手报告，不应再连打。

### 1.7 工程层可优化点（backlog，非本轮实现）

观察 ch6 重写过程暴露的工程缺口（**仅记录，不在本轮改**，符合「记录经验便于后续优化」）：

- **B1（中）run 终态 failed 的语义歧义**：`generate` 端点 run.status=failed 同时承载「生文失败」与「生文成功但质量环判债」两种语义，运维/SSE 消费方难以一眼区分。建议 run_status 增加区分字段（如 `failureKind: "generation" | "quality_debt"`），或在 message 里显式标注「正文已落库，质量环判债」vs「生文未落库」。当前 message「章节已保存，但检测到待修复问题」已部分区分，但 status=failed 仍易误导自动化监控。
- **B2（低）SSE ping 易被误判终态**：`ping` keepalive 事件无类型前缀区分，自动化监听易把 ping 当终态。建议 ping 用独立 `type:"ping"`（已是）且文档明确「只有 done/failed/error 才算终态」。
- **B3（中）avoidRetry 信号未被 generate 端点前置拦截**：qualityLoop feedback 已标 `avoidRetry: true`，但 `POST /chapters/:id/generate` 仍接受请求并跑完整轮生文→质量环→判债。若 generate 端点能在入口检查 latest feedback 的 avoidRetry，提前返回「需先调整 taskSheet 契约」提示，可省一整轮生文+审校的 wall-clock 成本。注意：这不能变成「自动拒绝重写」（会破监管只监控不代写），只是前置告知。

## 4. ch6 第二轮重写：planner LLM 输出畸形（新工程缺陷，非 D1/D2/D3）

### 4.1 现象

ch6 taskSheet 据第一轮 qualityLoop issueCodes 调契约后（补「仅何屿陆深具名出场」「不得主动发动源痕」「真同意后紧接代价致死」等约束，PUT 落库 815 字，无 internal code 被 strip），第二次起触发的 generate **全部失败**，且表象是 CF 524（公网）或长时间无首字节（pxed 本地直连）。

### 4.2 真根因（不是 CF 524，不是 D1 超时）

pxed server.err.log 反复 3 次 + server.out.log 8 次记录同一错误：

```
[error] POST /api/novels/.../chapters/cmrvs14ov.../generate Error: Planner output is missing objective.
    at Object.postValidate (.../plannerPlan.prompts.ts:169)
    at resolveStructuredOutput -> executeStructuredPrompt -> invokePlannerLLM
    at PlannerService.generateChapterPlan (PlannerService.js:599)
    at GenerationContextAssembler.assemble -> ChapterStreamGenerationOrchestrator.prepareRuntimeChapter -> createChapterStream
```

`POST /chapters/:id/generate` 的执行链：**planner 先行**（`planner.chapter.plan@v1` 生成章节执行规划 JSON）→ writer 才生文。本轮 gemini-3.7-flash-high 作为 planner 输出了畸形 JSON：

- title 字段塞满模型 hallucination 的元描述复读，例如：
  `"第6章 真同意：残痕托付与代价即死后的深渊对峙（总第6章）[残痕][托付][12000字][已校对修改完整版第6章结构规划][严禁截断][已对齐短宪法20章功能纲与真同意硬规则][仅何屿陆深具名出场]..."`
- objective 字段缺失/解析为空
- `postValidate`（`plannerPlan.prompts.ts:169`）抛 `Planner output is missing objective`
- semantic-retry-1 重试（latencyMs≈9917ms）后**仍畸形**（rawChars=1072，outputChars=4410 但 objective 仍空）
- `resolveStructuredOutput` 抛错 → generate 返回 500

### 4.3 为什么表象是 524 而非 500

planner 跑了 invoke + semantic-retry，每次 ~10s latencyMs，叠加前置 context 加载（contextBlockIds 含 novel_overview/chapter_target/state_driven_goal/state_snapshot/volume_summary/book_plan/arc_plans/story_macro/book_bible 9 块），总耗时 >100s 触发 CF Tunnel 524。公网 curl 收到 524 页面（16 字节 `error code: 524`）。本地直连 pxed `127.0.0.1:3000` 绕过 CF，但 curl 仍要等 planner 抛错才收到 500——之前我杀 curl 太早没等到 500，误判为「首字节慢」。

### 4.4 与 D1/D2/D3 的关系

**完全无关**。D1 修的是 writer 阶段超时预算，本故障卡在 planner 阶段（writer 还没被调用）。D2 的 timeout 分类针对 writer/prompt 失败，此处是 planner postValidate 业务校验抛错（非超时）。D3 的 stub 落库针对质量环持久化失败，此处根本没到质量环。第一轮 ch6 重写成功（planner 恰好没出垃圾输出），第二轮起 planner 持续输出畸形——是 planner LLM 稳定性问题，非返工重写目标。

### 4.5 planner 畸形输出鹦鹉了新 taskSheet 约束

注意：planner 输出的 title 垃圾里包含了「仅何屿陆深具名出场」「追兵仅环境压力不具名」「能力呈现不可控」——这些是我刚 PUT 进 ch6 taskSheet 的新约束文本。说明 taskSheet 被注入了 planner 的 context，但 planner 模型把这些约束当成要输出的 title 内容来复读，进一步污染了输出结构。**但根因不是 taskSheet 内容**（第一轮用旧 taskSheet 也成功过；planner 畸形输出是模型在 json_schema 策略下的稳定性问题），taskSheet 约束文本只是被畸变挪用进了 title。

### 4.6 经验提炼

1. **CF 524 是症状不是根因**。generate 端点 524 时，必须查 pxed server.err.log / server.out.log 看是哪一阶段抛错（planner / writer / acceptance / artifact_delta），不能停留在「CF 超时」层面。本轮 8 次 524 全是 planner postValidate 抛错导致。
2. **generate 执行链 planner 先于 writer**。`ChapterStreamGenerationOrchestrator.prepareRuntimeChapter` → `GenerationContextAssembler.assemble` → `PlannerService.generateChapterPlan` → planner LLM → postValidate → 才进 writer。planner 失败时 writer 根本不启动，D1 的超时预算无从验证。
3. **planner LLM（gemini-3.7-flash-high）在 json_schema 策略下偶发输出畸形 JSON**：title 字段复读元描述、objective 缺失。semantic-retry 一次不够（retry-1 仍畸形）。这是 planner 稳定性缺陷，需独立排查（见 §5 backlog）。
4. **本地直连绕不过 planner 故障**。CF Tunnel 是公网路径的额外 100s 限制，但根因在源站 planner；ssh pxed 直连 `127.0.0.1:3000`（`--noproxy '*'` 避开 Privoxy 劫持 localhost）能拿到真实 500，但解不了 planner 本身的输出畸形。

### 4.7 决断：ch6 停手，不在本轮回调

planner 畸形输出是**新工程缺陷**，超出「调 taskSheet 重写」能解的范围。连打 generate 只会重复 planner 失败（已 8 次）。按铁律「卡住先查根因，不无脑重试」停手。ch6 taskSheet 契约调整本身是有效的（约束文本落库验证在位），但被 planner 故障挡在生文之前，无法验证契约调整对正文的效果。

## 5. 新 backlog（planner 稳定性，非本轮实现）

- **P1（高）planner LLM 输出畸形 JSON 的稳定性**：gemini-3.7-flash-high 在 `planner.chapter.plan@v1`（strategy=json_schema）上偶发 title 复读元描述 + objective 缺失，semantic-retry-1 仍畸形。需排查：(a) json_schema 策略对 gemini-flash 是否合适（vs json_mode / function_calling）；(b) planner prompt 是否过度鼓励「完整/严禁截断」类元描述（prompt 里是否有「严禁截断」「完整版」「标准工程级终态」等诱发模型复读的措辞）；(c) semantic-retry 次数是否需增加或换 retry 策略（换 model / 降 temperature）；(d) postValidate 抛错时是否可降级用 taskSheet 已有字段兜底而非整请求 500（注意不能破「不代写」——兜底只能用已有契约字段，不能凭空生成）。
- **P2（中）generate 端点 planner 阶段失败的错误透传**：planner postValidate 抛错时，公网经 CF 表现为 524（误导），本地为 500。建议 generate 端点在 planner 失败时尽早返回结构化错误（含 failurePhase=planner、plannerError），而非让请求拖到 CF 524。这能让运维一眼区分「planner 失败」vs「writer 超时」vs「CF 网络」。
- **P3（低）planner context 注入 taskSheet 的边界**：taskSheet 约束文本被 planner 当 title 内容复读。需确认 planner prompt 是否明确「taskSheet 约束是输入约束，不是要输出到 title 的内容」，避免约束文本污染输出结构。
- **P4（中）llm 日志 append 失败 Unknown system error -122**：server.err.log 反复 `failed to append dedicated llm log: Unknown system error -122, close`。这是 llm.jsonl 写入的文件系统错误（可能是 fd 耗尽或磁盘），非本轮根因但影响 llm 调用可观测性，需独立排查。
